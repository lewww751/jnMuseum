# Spec：济南市博物馆官网（演示项目）

Status: ready-for-agent

> 术语见 [CONTEXT.md](../../CONTEXT.md)，架构决策见 [ADR-0001](../../docs/adr/0001-spring-boot-vue-split-architecture.md)。
> 本 spec 是用户视角的综合；字段级 API 契约与验收清单以仓库 `docs/SPEC.md`（实施唯一契约）为准。

## Problem Statement（问题陈述）

济南市博物馆需要一个官方网站（馆名借用、内容全虚构的作品集演示项目）：观众目前没有线上入口了解馆内的常设与临展、近期社教活动、馆藏精选和参观须知；入馆名额也没有免费的实名分时预约渠道，馆方无法按日期和时段控制人流。同时，作为作品集项目，它需要完整走通"内容展示 + 活动展示 + 门票预约"三个核心功能，并展示国内主流企业技术栈的工程实践。

## Solution（解决方案）

构建一个仅中文的博物馆官网，前后端分离：

- **观众端**（暗色庄重视觉风格）：首页、展览列表/详情（常设/临展筛选与展出状态标签）、近期活动（状态标签与类别筛选）、馆藏精选（镇馆之宝标识）、参观指南与关于页。
- **免费实名分时预约**：观众查看未来 7 天的开放状态与时段余量，以"1 名主预约人 + 最多 2 名同行人"实名预约，全部入馆人占名额；凭 8 位预约码（附二维码）入馆，参观日前一天 24:00 前可整单取消。
- **馆方后台**：管理员登录后进行内容管理（展览/活动/藏品 CRUD 与上下架、图片上传、指南文案）、开放日与时段容量管理（月历式）、预约管理（筛选查询与当天核销），并有数据看板。
- **一键运行**：Docker Compose 起 MySQL + 后端 + Nginx 前端，一条命令演示完整站点。

## User Stories（用户故事）

**观众（浏览）**

1. 作为观众，我想在首页看到当期重点展览与"门票预约"入口，以便快速了解当前看点并开始预约。
2. 作为观众，我想浏览展览列表并按常设/临展筛选，以便找到感兴趣的展览。
3. 作为观众，我想看到每个展览的展出状态标签（正在展出/即将开幕/已闭展），以便判断现在去能否看到。
4. 作为观众，我想查看展览详情（展期、展厅、长文介绍），以便决定是否前往。
5. 作为观众，我想浏览近期活动列表并看到"即将开始/进行中/已结束"状态，以便安排参与时间。
6. 作为观众，我想按类别筛选活动，以便快速找到感兴趣的活动类型。
7. 作为观众，我想浏览馆藏精选并看到"镇馆之宝"标识，以便了解馆藏亮点。
8. 作为观众，我想查看参观指南（开放时间、交通方式、参观须知），以便规划行程。
9. 作为观众，我想阅读"关于本馆"概况，以便认识这个博物馆。
10. 作为观众，我想在手机上流畅使用全部页面，以便随时随地获取信息。
11. 作为观众，我想在页脚始终看到"本站为演示项目，内容虚构"的声明，以免把虚构信息当作真实馆方信息。

**预约者**

12. 作为预约者，我想查看未来 7 天每天的开放状态与上/下午时段余量，以便选择合适的参观日期和时段。
13. 作为预约者，我想看到闭馆日被禁用并显示原因，以免误选不可参观的日期。
14. 作为预约者，我想为自己并携带最多 2 名同行人一并实名预约，以便与家人朋友同日入馆。
15. 作为预约者，我想在填写身份证号时获得即时格式与校验位反馈，以便尽早发现录入错误。
16. 作为预约者，当任一入馆人证件号在目标日期已有有效预约时，我想收到明确的中文错误提示，以便改约其他日期或更换入馆人。
17. 作为预约者，当时段剩余名额不足时，我想看到"已约满"提示，以便改选其他时段或日期。
18. 作为预约者，当天时段超过截止时间（上午 09:00 / 下午 13:00）后不可再约当日，并得到提示，以便理解预约规则。
19. 作为预约者，我想在预约成功后获得大号 8 位预约码与二维码，以便入馆时出示核销。
20. 作为预约者，我想通过"预约码"或"手机号 + 任一入馆人证件号"两种方式查询我的预约，以便随时掌握预约状态。
21. 作为预约者，我想在参观日前一天 24:00 前取消整单预约，以便行程有变时释放名额给他人。
22. 作为预约者，当已过取消截止或预约已核销时，我想看到不可取消的具体原因，以便理解为何无法操作。
23. 作为预约者，我希望证件号在页面展示时被掩码（显示前 4 位和后 4 位），以免完整证件号泄露。

**管理员（馆方工作人员）**

24. 作为管理员，我想用账号密码登录后台，以便安全地管理官网内容与预约数据。
25. 作为管理员，我想在数据看板看到今日/明日各时段预约量、近 7 天预约趋势与统计数字，以便掌握预约态势。
26. 作为管理员，我想对展览、活动、藏品进行增删改查并控制上下架，以便维护官网内容。
27. 作为管理员，我想为展览/活动/藏品上传封面图片，以便页面图文并茂。
28. 作为管理员，我想在线编辑"参观指南"与"关于本馆"文案，以便及时更新实用信息。
29. 作为管理员，我想在月历上把某天设为临时闭馆或强制开放（覆盖周一例行闭馆）并填写原因，以便灵活管理开放日。
30. 作为管理员，我想调整某天某时段的名额容量，以便按实际情况控制人流。
31. 作为管理员，我想按日期/时段/状态/关键字筛选并分页查看预约单（含全部入馆人），以便快速定位与核对预约。
32. 作为管理员，我想在参观当天核销预约码，将预约单整单标记为已入馆，以便完成入馆流程。
33. 作为管理员，当预约非当日或非有效状态时，我想看到核销操作被禁用及原因，以免误核销。

## Implementation Decisions（实现决策）

- **架构（ADR-0001）**：前后端分离——Spring Boot 3.2.5 + MyBatis-Plus 3.5.5 + MySQL 8（后端），Vue 3 + Vite 5 + TypeScript + TailwindCSS（观众端自定义暗色主题）+ Element Plus（后台，亮色主题）；后台不拆独立工程，以 `/admin` 路由区承载并懒加载。Docker Compose（MySQL + 后端 + Nginx 前端）一键运行，站点入口 8081。
- **语言与范围**：全站仅中文；馆名借用、内容全虚构，页脚固定演示声明；免费不免票——无支付、无短信通知、无真实身份联网核验、无爽约黑名单；活动仅展示不提供报名；藏品仅精选展示而非数据库。
- **预约领域规则（R1–R12，TDD 唯一契约）**：预约窗口为今天起 7 天（含当天）；当天截止（上午 09:00 / 下午 13:00）；开放日默认周一闭馆、支持按日期覆盖强制开/闭；单据结构为 1 主预约人 + 0~2 同行人、单内证件号不得重复；身份证 18 位且校验 GB11643 加权校验位、小写 x 归一化；手机号正则约束；跨单查重按"证件号 + 参观日期"且只看非已取消单；容量默认 300、事务内防超卖；前一天 24:00 前可整单取消并即时释放名额；仅参观当天可核销；预约码为 8 位数字（首位非 0）、冲突重试 ≤5 次；查询与取消均支持双凭证（预约码，或手机号 + 证件号；取消须手机号匹配）。
- **时间处理**：所有领域逻辑统一 Asia/Shanghai 时区；领域规则类注入 Clock，生产用系统时钟、测试用固定时钟，保证可测性。
- **数据与种子**：DDL 与种子数据由仓库提供并幂等初始化（IF NOT EXISTS / INSERT IGNORE）；单管理员种子在应用启动时写入（BCrypt 哈希）。
- **API 契约**：REST + JSON，统一 Result 包装（code/message/data）；业务错误 HTTP 400 + 中文 message，未登录 401；后台接口 JWT（HS256，12 小时）过滤器守卫，仅登录接口放行；日期 `yyyy-MM-dd`、时间 `yyyy-MM-dd HH:mm:ss`；图片上传限 jpg/png/webp、≤5MB、UUID 文件名，经静态映射对外提供。
- **前端行为**：axios 统一拦截弹错、后台请求自动附 Bearer、401 跳登录；dev 环境代理 API 与上传目录；预约表单前端同样实现身份证校验位即时校验（最终以服务端为准）；预约流程为"选日期 → 选时段 → 填信息 → 成功页"分步表单，可回退。
- **视觉规范**：观众端暗色庄重（自定义 ink/panel 色阶 + 泉水青主色 + 陶土/鎏金强调色），标题衬线字体、正文系统字体，不引入 webfont；移动优先响应式。

## Testing Decisions（测试决策）

- **好测试的标准**：只断言外部可观察行为（规则的判定结果与面向用户的错误信息），不断言实现细节（SQL 形态、内部调用次序等）；时间相关行为一律通过注入 Clock 驱动，不依赖真实时钟。
- **缝 1（主缝）**：领域规则纯逻辑类（身份证校验、预约政策、开放日规则、时段常量）——无框架、无 DB 依赖，JUnit + 固定 Clock，覆盖预约窗口边界、当天截止、开放日四象限（默认闭/强制开/默认开/强制闭）、取消截止（前一天 23:59 可取消、当天 00:00 后不可）、核销资格、身份证合法/校验位错/长度错/非法字符。
- **缝 2（次缝）**：预约服务 + Mockito 模拟数据访问层——仅覆盖必须依赖数据库交互的规则：跨单同行人查重、容量边界（余 2 递 3 拒）、单内证件号重复、预约码冲突重试。
- **不新增缝**：控制器层不写 Spring 集成测试，前端不写单测。API 契约由 TypeScript 全量类型检查与 compose 环境的浏览器走查（验收清单）保障。
- **完成定义**：后端 `mvn test` 全绿且 `mvn package` 成功；前端 `npm run build`（含类型检查）零错误；compose 环境浏览器走查通过验收清单（六页有真实种子内容、预约全流程符合规则、后台 CRUD/月历/核销可用）。

## Out of Scope（不在范围内）

- 支付、售票、退费与票价体系（免费不免票）
- 短信/邮件通知、真实身份证联网核验、人脸识别
- 活动报名与活动签到（活动仅展示）
- 会员体系、多管理员与角色权限（单管理员）
- 爽约黑名单与信用惩戒
- 线上部署、域名、HTTPS、CDN、SEO 与访问统计
- 多语言（仅中文）、无障碍专项审计
- 真实馆方内容（展览/活动/藏品/文案均为虚构演示数据）

## Further Notes（补充说明）

- 种子数据规模：5 个展览、8 个活动、10 件藏品、参观指南与关于文案、若干演示预约单。
- 详细 API 字段级契约与验收清单见仓库 `docs/SPEC.md`（实施唯一契约），本 spec 是其上层的用户视角综合。
- 预约人数上限的口径：单笔预约 1~3 人（主预约人 + 最多 2 名同行人），每人都实名并各占 1 个名额。
